# FlashAttention forward on dav-2201

`910b.py` builds a generic and a pipeline variant from the same online-softmax
step. Pass `variant="generic"` for a serial KV loop or `variant="pipeline"` for
ordinary automatic `T.Pipelined`. Both use the numerical and input contract
below. The CPU oracle models block rounding; performance comparisons require
separate evidence from the selected hardware and installed Torch NPU version.

Inputs use contiguous `Q[B,Hq,Sq,D]`, `K[B,Hkv,Sk,D]`, and `V[B,Hkv,Sk,D]`.
Output is `O[B,Hq,Sq,D]`. Dimensions are positive, `Hq` is divisible by `Hkv`,
and consecutive groups of `Hq/Hkv` query heads share a KV head. Operand and
output dtype is FP16 or BF16. `D`, `block_q`, and `block_kv` are multiples of 16;
`Sq` and `Sk` may have tails. The expression supports neither dropout nor an
attention bias or arbitrary padding mask.
Inputs after operand rounding and the resulting FP32 scores must be finite.
Negative infinity used for masking and initial running maxima is part of the
algorithm. The CPU oracle diagnoses nonfinite inputs or score overflow.

For causal attention, key index `j` is visible to query index `i` when
`j <= query_start + i`. `query_start` is nonnegative and
`query_start + Sq <= Sk`; the first KV block therefore contains a visible key
for every query. Each query group visits only the KV tiles containing at least
one visible key. This loop bound uses the complete valid query group, so both
AIVs and the AIC agree even when one AIV has an empty tail partition. A tile
visible to the group's first query uses ordinary score scaling; the diagonal
and KV tail retain the per-element mask. Omitted tiles would leave the online
state unchanged, and the retained tiles keep the same P rounding points.
For noncausal attention all `Sk` keys are visible. The default scale is
`1 / sqrt(D)` and a supplied scale must be finite.

Scores, running maximum, denominator, and output accumulation use FP32. For
each KV block the algorithm updates

```
m_next = max(m, reduce_max(scores))
alpha = exp(m - m_next)
p = exp(scores - m_next)
l = alpha * l + reduce_sum(p)
o = alpha * o + cast_to_operand_dtype(p) @ V_block
```

It finally writes `cast_to_operand_dtype(o / l)`. The denominator sums FP32
probabilities, while the second Cube GEMM consumes rounded FP16/BF16
probabilities. Changing `block_kv` can change these rounding points. Generic
and pipeline variants with the same parameters have the same numerical
contract. `attention_reference` models these operations on CPU; it does not
model native instruction error or certify device execution.

The score DMA lands in a separate FP32 input tile, read only by scale/mask.
Its lifetime therefore ends before the destructive softmax work. Scaling
writes the work tile directly; this separation adds storage, not a UB copy.
After row max, the work tile is overwritten first by `scores - m_next` and
then by `exp(scores)`. These are separate ordinary Parallel steps with the same
FP32 subtraction and exp nodes. Exposing the dead score's replacement avoids
a second full tile for the subtraction result.

The pipeline variant exposes `alpha * o` as a separate FP32 Parallel task
before exporting P. The later FP32 add completes the same output epoch after
PV is ready. This lets the scheduler distinguish independent rescaling from
the operation that consumes PV; the generic variant keeps the complete update
after PV. Both retain the same multiply and add rounding points.

The Torch NPU reference uses `npu_fusion_attention(..., head_num=Hq,
input_layout="BNSD", sparse_mode=0, keep_prob=1)`, original `Hkv` K/V heads,
and a dense bool mask where `True` excludes a key. Causal exclusion is exactly
`j > query_start + i`, with unrestricted pre/next windows. This avoids relying
on a sparse causal mode's alignment convention for rectangular inputs. Torch
computes the same attention function, but its internal block rounding can
differ from this explicit per-block P rounding; comparisons need declared
dtype tolerances rather than bitwise equality.

`FwdTiling` controls `block_q`, `block_kv`, and the automatic pipeline search
bound `max_stages`. Q stays in L1 across the KV loop; K and V are loaded once
per iteration. These cache and traversal choices live in the Python algorithm.
The compiler chooses issue order, stages and buffer versions under the target
capacity checks. A `max_stages` value is a search bound rather than a promised
stage count or performance estimate.

`query_grouping=2` explicitly groups two adjacent query tiles in one block.
Both use the same imported K/V tile, while their Q caches, FP32 online state,
and UB work tiles remain independent. L1 P and the QK/PV L0C accumulators are
shared through ordinary data dependencies. The mathematical step above is
the same macro for both queries and both variants. This is a Python cache
policy using serial or ordinary automatic `T.Pipelined`; it supplies no stage,
buffer-version or event hints. The default `query_grouping=1` retains one query
tile per block.

For causal prefill the grouped KV loop covers the longest valid query prefix.
The first query tile still executes only its own prefix, so grouping introduces
no extra completely masked updates to its recurrence. A second tile absent
from an odd final pair has zero valid rows and executes neither initialization,
the query step, nor output export. For packed decode, grouping combines adjacent
head tiles within the same KV-head group; all their rows retain the single
`query_start` position. Grouping never crosses a batch, a prefill query head,
or a decode KV-head group. The four BNSD parameters and probability-rounding
points are unchanged.

Two independent query components require more resident state and scratch.
An otherwise legal single-query tiling can therefore fail target storage
checks with grouping 2, including a wide default KV tile. The
factory does not silently shrink either tile or bypass these checks. An
explicit smaller tiling can be evaluated as another algorithm configuration.
This grouping policy does not claim to reproduce the installed Torch kernel's
cache policy or imply a performance improvement.

With `tiling=None`, `block_kv` is the smallest of 64, 128 and 256 covering
`Sk`, and 256 for longer sequences. Longer KV blocks reduce the number of
online-state updates and C/V handoffs, while increasing Score/P and K/V tile
storage; short sequences avoid padding to an unnecessarily wide single tile.
This is a throughput starting point, not a measured cost model or a universal
performance guarantee. The query tile starts at 64 for prefill and uses the
packed-head rule below for decode. Both are capped by a logical output-tile
target of 8192 elements: round `8192 // D` down to a multiple of 16, with a
minimum of 16 rows. Thus D128 keeps 64 rows and D256 uses 32 rows. This controls
the size of FP32 output/state tiles without reproducing the compiler's scratch,
buffer-version or alias planner. The minimum row tile can exceed the element
target for D above 512; every configuration still needs final resource
validation. The stage search bound remains 4.
An explicit `FwdTiling` remains authoritative, including `FwdTiling()`'s
64/64/4 values. A plain dictionary is also accepted and must contain exactly
the three integer fields `block_q`, `block_kv`, and `max_stages`; unknown or
missing fields are diagnosed. The CPU oracle's `block_kv=None` follows the
same default KV width; pass an explicit width to model another candidate's
probability-rounding points.

`get_tuning_configs` accepts the six problem dimensions and the same dtype,
variant, causal offset and scale arguments as the factory. It returns complete
JSON-serializable factory kwargs, keeping the default query tile and stage
bound while trying up to three KV widths, 64/128/256. For a short sequence it
omits widths larger than the smallest covering width. The search has no
benchmark-shape table or duplicate resource planner. Candidates can still be
rejected by the target compiler's resource checks; unsupported runtime or
device failures must not be treated as a slower candidate.
The optional `query_groupings` argument is a nonempty tuple or list of unique
integers from `(1, 2)`. Its default `(1,)` preserves the three-candidate limit;
pass `(1, 2)` to opt into both grouping policies. Every configuration contains
the complete problem, an integer `query_grouping`, and the three-field tiling
dictionary, so JSON round trips remain direct factory inputs. Grouping does
not change the query-tile default or add a Python resource estimator.

Use the existing tuner directly with these complete configurations:

```python
from tilelang.autotuner import AutoTuner

configs = get_tuning_configs(
    1, 4, 4, 1024, 1024, 64, dtype="float16", variant="pipeline"
)
tuner = AutoTuner.from_kernel(flash_attention_fwd, configs).set_compile_args(
    out_idx=[3], target={"kind": "ascend", "arch": "dav-2201"},
    execution_backend="tvm_ffi",
)
```

Supply a matching Torch reference and input policy through the tuner's existing
`set_profile_args`, then run on the explicitly selected logical NPU. The full
problem and tiling values stay in each configuration; no shape-capturing
wrapper or second tuning implementation is required. Recheck a selected
candidate with matching inputs and declared dtype tolerances before treating
its timing as performance evidence. Different KV widths can change numerical
rounding, even when they implement the same attention function.

For `Sq == 1`, matrix rows represent consecutive query heads within one KV
head's group. Each block scans K/V once for up to `block_q` heads. Q/O use
contiguous three-dimensional views of the original BNSD parameters; callers
keep the same four arguments. All packed rows have the causal position
`query_start`, independent of their head index. Unused physical Q rows are
zero initialized. With no explicit tiling, `block_q` is the group size rounded
up to 16 and capped at 64 and by the same output-element target; explicit
`FwdTiling` remains authoritative. Groups
larger than the tile use multiple blocks, each confined to its own KV head.
This is a Python traversal choice, using the same online-softmax step and
ordinary automatic pipeline as prefill. It introduces no split-KV merge.

The kernel carries the valid `qrows` extent on the score, P, PV,
and output copy regions. All connected UB buffers retain one logical row
capacity until ownership lowering gives each AIV its private rows. The GM
handoff owns group isolation and L1 tail initialization. The user does not
allocate reduction scratch, encode two AIV offsets, or issue synchronization.
The running maximum updates through an ordinary FP32 tile copy over `qrows`;
it preserves the stored bits and exposes the next iteration's state dependency.
The backend lowers this state copy to a native bit-preserving UB operation,
with the same bounded element count used for a dynamic tail or an empty owner.
Masking uses ordinary selection, rescaling uses ordinary `max` and `exp`, and
normalization uses ordinary division. There is no combined softmax primitive.

Before performance comparison, the integration must pass CPU IR/codegen checks,
CANN offline compilation, and a small same-card correctness comparison. Compare
both variants against the same installed Torch NPU attention implementation,
with matching layout, GQA, causal offset, scale, dtype and output contract.

## Persistent paired-query attention

`persistent_910b.py` exposes `persistent_attention_fwd`. It expresses dense
noncausal MHA with a fixed group grid and an immutable task clock across each
group's query pairs. It is a separate algorithm expression from the generic
and automatic pipeline variants above. It has no GQA, causal or padding mask,
dropout, bias, or sequence tails. Operands and output use FP16 or BF16; scores,
online statistics, and output state use FP32. Inputs and resulting scores must
be finite. The softmax scale is `1 / sqrt(head_dim)`. The online recurrence and
per-KV-block probability rounding are the same as described above.

The factory takes keyword arguments `batch`, `heads`, `query_pairs`,
`kv_tiles`, `groups`, `block_q`, `block_kv`, `head_dim`, `row_block`, `dtype`,
and optional cache and vector-grain parameters below.
All dimensions and `groups` must be positive integers. Tile dimensions and
`pv_rows` must be multiples of 16; the Vec1 `row_block` and Vec2
`row_block_vec2` must be multiples of 8 dividing `block_q`. Vec2 defaults to
the Vec1 grain. `pv_rows` divides `block_q`, and
`groups` must divide `batch * heads * query_pairs`. The factory diagnoses these
shape contracts before constructing IR. The target compiler still checks
physical resource feasibility; alignment alone does not guarantee admission.

`pv_chunk=None` stages the complete P/V tile for each PV GEMM. An explicit
positive multiple of 16 dividing `block_kv` stages PV through smaller L1
chunks. For example, `block_kv=1024, row_block=16, pv_chunk=256` keeps one
logical 1024-key softmax step while loading 256-key P/V chunks for PV. Set
`kv_tiles` to the intended number of logical blocks; the factory does not
change sequence length or UB row granularity implicitly. `pv_chunk` is an
L1 staging extent, not a request for the native Cube K size.

In this path each V chunk is loaded once and consumed by both query owners.
The two owners have distinct FP32 L0C accumulators with one compiler version;
each accumulator clears only on the first chunk and is exported once after
the complete logical K reduction. P retains the GM row pitch of `block_kv`.
The compiler lowers QK into physical M/N tiles, reserves the complete root
L0C footprint, and checks both owners' readers before V-slot reuse. Neither
PV staging nor physical QK tiling adds a softmax epoch or intermediate P
rounding point.

The same factory also expresses the following choices. They are ordinary DSL
storage/traversal policies, available to direct calls and existing autotuning.

| Parameter | Meaning |
| --- | --- |
| `row_block_vec2` | Independent output-update UB grain; defaults to `row_block` |
| `separate_score_input` | Separate Score DMA input from the destructive FP32 work tile; defaults to false |
| `inplace_final_division` | Normalize the final dead FP32 output in place before casting; defaults to true |
| `qk_chunk` | Optional aligned N chunk; Q stays in explicit L0A across the owner's QK chunks |
| `cache_pv` | Retain full V in L1 and a full-KV P cache per M part; defaults to false |
| `pv_rows` | M part of cached PV; defaults to `block_q`, requires `cache_pv` when different |
| `preserve_issue_order` | Validate and retain the fully specified outer issue order; defaults to false |

`qk_chunk` is positive, 16-aligned and divides `block_kv`. Cached PV requires
an explicit `pv_chunk`. It loads V once per task for both owners, loads P once
per owner and M part, then uses ordinary automatic `T.Pipelined` over the K
slices. Each complete `pv_rows` FP32 accumulator clears on chunk zero and
exports once after the final chunk. This differs from the default chunk-staged
V path above, while preserving its online mathematics and four-argument ABI.
Independent Score staging costs an additional FP32 input tile. Cache sizes,
grains and versions remain subject to target resource and completion checks;
valid shape parameters alone do not guarantee compilation or performance.
`preserve_issue_order=True` supplies a complete outer plan rather than a
performance search. It preserves issue order, stage and explicitly fixed
versions, and deterministically completes unspecified versions with the minimum
counts required by dependencies. Illegal ordering or insufficient storage,
stage bounds or fixed versions are diagnosed; the compiler does not silently
reorder the plan to admit it.
The nested automatic PV loop remains a separate scheduling domain. The
default retains the existing partial `Stage` contract and cross-pipe search.

For long dense inputs, this module's `get_tuning_configs` returns two finite
cached-PV policies with BQ64 and logical BK256/BK512. It takes `batch`, `heads`,
`query_len`, `kv_len`, `head_dim`, and optional `dtype`, `groups` and
`preserve_issue_order`. Pass its dictionaries to the existing
`AutoTuner.from_kernel(persistent_attention_fwd, configs=...).set_compile_args(
out_idx=[3], target={"kind": "ascend", "arch": "dav-2201"})`. Both candidates retain the
input KV length. Both use complete 64-row PV accumulators and 128-wide PV
K slices, so each owner loads a cached V slice once instead of once per
32-row part. Vec1 uses `min(64, 8192 // block_kv)` rows (32/16 respectively),
independently of D; Vec2 keeps 64 rows. This reduces repeated vector setup and
small reductions without changing the logical BK or P rounding point.
These are finite starting policies, not a measured cost model. At D128 the
BK256/BK512 plans use 192/352 KiB L1, 32 KiB L0A and 64 KiB L0B; their private
UB allocations are still checked by the compiler. Larger BK reduces online
state updates and GM handoffs but
increases residency and changes the P rounding boundary; compare it as an
algorithm policy, separately from compiler changes. Candidates still need
normal capacity and numerical validation. The factory remains available for
the other complete-tile, streamed and cached policies above.

The returned PrimFunc takes `(Q, K, V, O)`. These contiguous tensors must
not alias one another.

| Argument | Shape | Dtype |
| --- | --- | --- |
| `Q`, `O` | `[B,H,query_pairs,2,block_q,D]` | operand dtype |
| `K`, `V` | `[B,H,kv_tiles*block_kv,D]` | operand dtype |

For standard BNSD input, `Sq = query_pairs * 2 * block_q` and
`Sk = kv_tiles * block_kv`. Q/O are ordinary reshape views; K/V already use
BNSD. There is no transpose or input copy in this adaptation.

Score, P and PV use `T.alloc_workspace` for one logical task generation.
The compiler plans their bounded rings; host lowering allocates aligned GM
storage on the caller's stream and manages its lifetime. OState uses the same
allocator with explicit `[groups, owner, query_slot, block_q, D]` dimensions
and one compiler version. Its two query slots express algorithm state
ownership, independently of the task-generation rings. No scratch needs
caller initialization or an additional kernel argument.

An ordinary `T.copy(OState[group, sid, query_slot, rows, :], output)` loads
FP32 state into private UB. Separate Parallel operations rescale and add PV,
then a copy saves the next state. The first KV tile initializes from PV and
the last normalizes into O. Choosing GM for this state is Python storage
policy; dependency analysis and synchronization protect its actual regions.

Each mixed-core group contains one AIC and two AIVs. Local pair `p` in group
`g` owns flattened pair `g + p * groups`, decoded in ordinary batch, head,
query-pair order. The two AIVs own the two complete `block_q` query blocks;
`row_block` only subdivides each AIV's private UB computation. The
`annotate_aiv_private` declarations preserve those complete local domains.
The AIC computes QK and PV for both owners. GM workspaces retain explicit
group and AIV-owner axes, so their logical regions are disjoint.
Task-generation versions are additional dimensions created by the compiler.

Score, P, PV and alpha each request two automatic versions. With
`pv_chunk=None`, V in L1 also requests two versions. Their slots follow the
compiler-owned logical task generation. Streamed PV requests two V versions
owned by its nested automatic chunk loop; Python supplies neither a slot
dimension nor chunk parity. Both query owners read each generation before
the compiler permits its reuse. Maximum,
denominator, and OState alternate by the **local pair's** parity; flattened
pair parity would fail to alternate for an even group stride. For each query,
the first KV tile starts O from PV. A later tile reads FP32 OState, multiplies
by alpha, and adds PV through separate ordinary Parallel operations. A
nonfinal tile stores FP32 OState to GM. The final tile performs ordinary
division by the denominator, casts, and writes O. The state belongs to this
group for the whole task clock, including fill and drain.

One `T.serial(tasks)` loop decodes a logical task once for all four phases:
QK uses Stage 0, Softmax and PV Stage 1, and UpdateO Stage 2. The compiler
shifts the task coordinates, accesses and synchronization together, generates
valid fill/drain guards, and extends the physical execution interval. Python
contains no `tasks + 2`, delayed-task arithmetic or task-slot parity.
The single stream spans all local query pairs; it does not drain after each
query. First/last-KV predicates remain ordinary algorithm conditions.

Stages fix phase offsets and source order within each pipe. Stage-only mode
still allows cross-pipe search; `preserve_issue_order=True` supplies the full
outer issue order and bypasses that loop's scheduling search. Both consume
the same dependency, version, capacity and completion contracts. Nested PV
pipelining remains independent. This manual strategy is not an assertion that
the automatic optimizer discovered it.

Native completion covers both AIV owners and all row subtiles before a
collective handoff is ready, and all readers before reuse. The existing mode-2
paired completion is retained. The AIVs do not advance as independent query
pipelines; this differs from Torch Matmul KFC's independent-progress contract.

Frontend region coverage, native finite completion, CANN compilation, and
same-card numerical comparison are separate validation gates. Performance
claims require a matching installed Torch NPU comparison and profiler
evidence; none follow from this expression or its phase hints alone.
